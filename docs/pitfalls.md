# 踩坑清单

分两类：**已验证**（之前实际踩过并有解法）、**待验证**（这批站点可能遇到但没实测过）。

写代码时遇到渲染或抓取异常，先查这里。

## 一、已验证

### 1. 公式被写成反引号

旧版知枢产物把公式包在反引号里当行内代码，KaTeX 不渲染，页面上就是一段等宽字。

处理：抽取时把 `` `$...$` `` 与 `` `$$...$$` `` 剥掉外层反引号，交给 KaTeX。不要试图正则识别裸公式，误伤率高。

### 2. Mermaid 依赖 CDN

部分站点 Mermaid 走 CDN（优先 npmmirror，多源超时回退）。断网或 CDN 抽风时图不出来。

处理：不走任何远程源。批 3.5 的实际落地形态是 **npm `mermaid@12.3.0` + Vite 动态 `import()` 分包**
（`mermaid.core` 656KB，连同它展开的 57 片合计 5,106KB，只在阅读页第一个围栏可见时才取），
不是手放的 `vendor/mermaid.min.js`——首屏 chunk 里一个 mermaid 实现字节都没有。

### 3. 离线内联不全（以及「零 CDN」这条禁令怎么落地）

所谓"单文件、断网可开"，实际常有漏网的远程字体或图标请求。

处理：构建后跑一次静态扫描——批 3.5 起收进 `tools/check_offline.py`（不再手 `grep`），
把 `http://`、`https://`、`//` 协议相对按「资源加载位点 / xmlns 声明 / 代码块与 JSON 字面量 / 保留域名 /
纯数据」分类，只有资源加载位点上的远程 URL 判违规；由 `tools/selfcheck.py` 调用并并入报告（决策 3 落地）。

**但判定标准是「运行时会不会真的发请求」，不是「文本里有没有 URL」**——铁律原文写「零 CDN」是表述错了，
已改为「渲染结果不得在运行时发起任何网络请求」（同步改在 `.qoder/rules/zhishu-rules.md`、
`.lingma/rules/zhishu-rules.md`、本条与 `AGENTS.md` 摘要）。白名单三类：

| 类别 | 为什么放行 | 批 1 实测 |
|---|---|---|
| `xmlns` / `xmlns:xlink` 声明 | 内联 SVG 必需的命名空间声明，浏览器不会去取这个地址 | `www.w3.org` 13 处，**13/13 全在 `xmlns="http://www.w3.org/2000/svg"` 里**（economics 两本的内联 SVG 图）〔X〕 |
| 代码块 / 示例数据内的 URL | 属被展示的内容，不会被解析成资源 | `weather.example.com` 2 处，**2/2 都在围栏代码块的 JSON 字面量里**（`"url": "https://weather.example.com/a2a"`）〔X〕 |
| 保留域名 | `example.com`/`example.org`/`example.net`/`localhost`/`127.0.0.1`/`0.0.0.0` 不解析到真实服务 | 与上一类重叠，无独立命中〔X〕 |

白名单之外才是真外链，**降级为纯文本**：保留显示文字、去掉 href、加标记「原文链接，离线不可达」，
逐条记 `_report.json` 的 `externalLinks`（路径 + 上下文行）。批 1 实测真外链 **13 处，全是
`mp.weixin.qq.com/s/…`**，形态是 Markdown 自动链接 `<https://…>`，集中在「来源」小节〔X〕；
`tools/extract.py --link-policy strip` 已实现三种形态的降级（`[文字](url)`、`<url>`、裸 URL），
默认 `keep` 只记录不改正文。检测器实现见 `extract.py::classify_links`（`XMLNS_RE` 只认属性名结尾的上下文，
`fence % 2` 数围栏判断代码块内）。

### 4. `\u002F` 反转义

内联数据里的路径斜杠被 JSON 转义成 `\u002F`，直接拼进 `src` 会 404。

处理：解析后统一 `json.loads` 两次或 `str.replace('\\u002F', '/')`。

### 5. 中文文件名的 raw URL 必须编码

`https://raw.githubusercontent.com/zrx-11/{repo}/main/交付说明.md` 直接请求会 404 或乱码。

处理：`urllib.parse.quote(filename)`。目录名同理，如 `01-Hello-AI人工智能导论`。

### 6. 本机系统代理导致请求超时

走默认 opener 时会被本机代理拦截，40 个站批量抓取会大面积 timeout。

处理：`urllib.request.build_opener(urllib.request.ProxyHandler({}))`，显式禁用代理。

### 7. 旧 schema 缺 three 个字段

早期产物（本地 `1\11` 那批数学书）`concepts` 只有 `id/title/file/chapterIds`，缺 `prerequisites`、`depthFragment`、`claims`。

处理：这不是解析 bug，是数据缺口。抽不到就留空，不补造。诊断倒推功能对这类站点降级为"无前置链"。

2026-11-24 probe 修正了这个判断的适用范围〔M〕：GitHub 上的三站 **`prerequisites` 不缺**（章节非空 19/20、13/14、15/16，概念 49/50、58/61），
真正普遍缺的是另外两个——`depthFragment` 非空只有 10/50 与 5/61，`claims` 三站恒空（math-physical 有顶层 `claims: []`，hello-ai 与 sudoku 连键都没有）。
所以「旧版普遍缺前置链」只适用于本地旧批次，不适用于已跑过知枢流水线的站点。

### 8. 交付说明的数字不可直接信

`交付说明.md` 里"20 章、50 概念、60 测验"这类表述格式不统一，正则容易抓到"第 3 章"或题号。

处理：计数以实际抽出的数组长度为准，说明文档只作为交叉校验，不一致时记入 `_report.json`。

**批 1 首跑坐实了这个判断，并给出一条可复用的解释**：`hello-ai-zhishu/交付说明.md` 自述 14 章，
`manifest.json` 实测 **20 章**，而概念/题/卡/术语四项完全一致（50/60/70/110）〔X〕。差的 6 章不是抽错，
是说明文件只数了正章：**id 为 `ch01`–`ch14` 是 14 个正章，另有 `t01`–`t06` 六个「专题」**
（`专题 1：一句话的旅程`、`专题 2：推荐系统…`、`专题 6：AI 与开源`），专题属附录类内容，作者没写进说明。
两个结论：

1. **提取器的数字只认 manifest，说明文件仅作交叉核对**；差值不解释清楚就不写进任何展示层。
2. `chapters[].num` 必须由 id 尾部数字解析，且**同书内可重复**（`t01` 与 `ch01` 都会得 `num=1`）——
   所以 `num` 只能当显示序号，不能当键，也不能按它排序去重〔X〕。

### 9. 单文件大包的能抽出来，但内联正文不能当正文用

原「待验证 1」，2026-11-24 定案。`math-physical-methods` 的 `index.html` 1,887,845B，内联数据靠括号配平扫描 + 反转义后
`json.loads` 能稳定命中 `BOOKS` 容器 846,220B〔P〕，抽取本身没问题。

**但后半句才是结论：内联的正文是成品 HTML，不是可还原的 Markdown。**实测 `BOOKS[slug].rendered` 里
`ch01` 含 KaTeX 节点 204 个、`alttext` 计数 0、公式定界符（单/双美元符）计数 0〔H〕——原始 TeX 在站点构建时已被烤掉，取不回来。
所以 `body` 只能回读该站的 `.md` 源文件，`rendered` 降级为「有成品页，公式不可还原」，对应 `schema.md` 的 `contentLevel: "degraded"`。

同文件另有 610 个体积更小的容器，其中 `jM` 22,063B 是混淆代码（无引号键 141 处、无空格）〔P〕——
**必须按体积排序再逐个核对，不能取第一个命中就当数据。**

### 10. 数独站的正文不在 `src/content/*.js`，走 Node 求值分支

原「待验证 3」，2026-11-24 定案。`sudoku-zhishu` 的 `src/content/*.js`（`seeds.js`、`lessons-a.js`、`lessons-b.js`、`quizzes.js`、`meta.js`）
是**构建输入**，运行时的正文已经拼进 `index.html` 的 `ZS.*` 命名空间里〔T〕〔N〕：`ZS.lessons` 16、`ZS.quizzes` 54、
`ZS.CARDS` 34、`ZS.GLOSSARY` 43、`ZS.SEEDS` 14、`ZS.TECH_META` 6〔N〕。

这些是 JS 字面量不是 JSON（无引号键 233/248 处、模板串 20–24 个、注释 10 处、尾逗号 46–48 处〔P〕），Python 侧解不了，
**数独走 Node 求值分支，抽取器因此依赖 Node 运行时**（`new Function('return ' + 字面量)()`，本轮已跑通〔N〕）。
Node 不可用时该站降为 `stats-only` 并记 `_report.json`，不自动安装运行环境。依赖版本见 `tools/README.md`。

另外它的正文片段本身是 HTML（16/16 章含 `<p>`，8/16 含 `<table>`，公式定界符计数 0）〔N〕，
与 `chapters[].body` 的 Markdown 契约不符 → 靠 `bodyType: "html"` 区分，前端不要按 Markdown 渲染。

### 11. 内联赋值取「首个括号」必错

`sudoku` 的 `ZS.lessons = (ZS.lessons || []).concat([ … ])` 这类写法，等号后**第一个** `[` 是 `(ZS.lessons || [])` 那个空数组，
按「首个括号配平」取容器会拿到 2 字节的 `[]`，正文一条不剩〔P，本轮 probe 修正过程〕。

处理：在窗口内枚举所有候选容器，取**配平后最长**的那个；`.concat(` 只在紧邻（80 字符内）时视为同一赋值。
点号命名空间的赋值（`ZS.x = …`）要单独一条正则，`const|var|let|window.` 覆盖不到。

### 12. 同一份数据的两套 id 命名空间

`manifest.json` 的 `quizzes[].id` 是 `q01`，`index.html` 内联 `BOOKS[slug].manifest` 里同一条是 `ch00-q01`〔H〕〔M〕，
两站如此（各 60/100 条全部不同）。顶层键与其余字段逐项相等〔M〕。

处理：批 1 必须**显式选源**——统一取 `manifest.json` 文件侧，内联副本只用于结构对账，不作数据源。
混用会让题目 id 对不上，倒推诊断链直接断。

### 13. 字段名撞车：`source` 已被占用

统一 schema 原本想用 `source{repo,path}` 记抽取来源，但实测三站 manifest 的 `source` 是「原书出处」对象
（hello-ai `{"file":"hello-ai.pdf","page":"6–15"}`、math-physical 无 `page` 键、sudoku `page` 是整数 0）〔M〕。

处理：抽取来源改叫 `origin`，原书出处原样承接为 `bookSource`，`page` 不规范化。
同步点：`schema.md` 第一/三/四节、`design.md` 详情层回溯条、`sites.md` 第八节——只改 schema 会让三处表述打架。

### 14. 拉了 `*.csv` 才发现 kaoyan 的 csv 是校对台账，不是题库

`kaoyan-math-66000` 原本只稀疏检出根目录，2 个文件。按「加 `*.csv` 与 `*.txt`、不加 `*.html`」的决策放宽到任意深度后：
已检出 **2 → 75**（md 28 + json 20 + **csv 19 + txt 8**），pack 205.54 KiB → **386.76 KiB**〔K〕。

打开 csv 一看，表头是 `q,page,verdict,note,time` 与 `qno,册内编号,页,题干核对,答案核对,校勘位置`——
**这 3,613 行是人工核对台账（哪题第几页、判定、备注），不是题面**；
`work/manifest/*.json` 也是流水线元数据（`waves.json`、`inventory.json`、`q2p`/`p2q` 映射）〔K〕。
真正的题干与答案只在那 **201 个 `.html`** 里，而成品 HTML 不拉（理由见下）。

结论：**kaoyan 的正确判定是 `stats-only`，不是「有题无正文的 degraded」**——它连题面都拿不到。
「degraded = 可做题、无或极少正文」这个定义本身保留（sudoku 就是标准 degraded：16/16 章 HTML 正文 + 54 道题），
但 kaoyan 不进这一档。以后遇到「有题库数据」的站，先 `head` 两个数据文件看表头再定档，不要按扩展名猜。

公式定界符顺带验了：台账文本里 `$...$` 149 处、`\(...\)` 332 处〔K〕——**定界符完好**，
但 `\(...\)` 这种写法要求 KaTeX 端开 `inlineMath: [['$','$'],['\\(','\\)']]`，或抽取时归一成 `$...$`（已写进铁律）。

### 15. 三档拉取的扩展名清单：`*.md *.json *.csv *.txt`，明确不含 `*.html`

`*.html` 不拉的代价是认下来的：知枢单文件站的 `.html` 与 `BOOKS[slug].rendered`、sudoku 的 `ZS.*` 正文是同一类东西——
**公式在生成时被烤成 KaTeX 节点、并绑死当时的字号与配色**，反解析成本高、收益低（`math-physical` 实测
KaTeX 节点 204 个、`alttext` 0、定界符 0〔H〕）。kaoyan 的公式密度又极高，硬啃 HTML 只会产出看着对、
实际不可重排的正文。所以三档模式固定为 `*.md *.json *.csv *.txt`，写进 `tools/clone_repos.sh` 与 `tools/README.md`。

### 16. `setAttribute('hidden','false')` 等于继续隐藏

批 3 阅读层第一版面板「关不掉也打不开」，查下来是这行：

```ts
els.panel.setAttribute('hidden', String(visible));   // visible=false 时写成 hidden="false"
```

`hidden` 是**存在即生效**的布尔属性，值写 `"false"` 照样命中 `[hidden]` 选择器——元素仍然不显示，
且 CSS 里只要有一条 `[hidden]{display:none}` 之外的 `display` 覆盖，还会反过来出现「关不掉」。

处理：统一走 `el.hidden = !visible` 属性赋值（`src/panel.ts:341`）。
JS 里读 `el.hidden`，不要在 CSS 里用属性选择器猜值。

### 17. 章节→概念的反查只能走 `concepts[].chapterIds`

`design.md` 第三节说「概念是立柱上的发光点」，但挂载关系有两个候选字段，取错就是一片空立柱〔X〕：

| 字段 | 非空数 | 结论 |
|---|---|---|
| `chapters[].conceptIds` | **15 / 1,169** | 抽取器普遍留空，不能用 |
| `concepts[].chapterIds` | **765 / 765** | 全部可解析，唯一可用路径 |

处理：`layout.ts::conceptsByChapter()` 拿全书概念按 `chapterIds` **反绑**到章，一章多概念全挂、不截断。
`chapters[].conceptIds` 仍留在类型里（可选字段），只作交叉校验，不作渲染源——
这正是「铁律 7 抽不到留空」在下游的代价：**空数组是真数据，不能拿它当关系表用**。

### 18. 同一个 `bookSlug` 分布在多个仓库，定位必须带 file

129 条书目里 `bookSlug` 只有 **98 个不同值**——**31 个 slug 出现在 2 个及以上仓库**
（同一本书的中英版、或不同作者复用同名 slug，如 `hello-ai`、`d2l`、`rl-sutton`、`zhengshi`）〔X〕。
按 slug 找书会命中错的那本，自检的「打开指定章节」也会点错展台。
注意这与 `totals.sitesUnique = 96` 不是同一口径：后者按抽取的结构签名去重〔X〕，前者按字符串。

处理：唯一键是 `repo + bookSlug`，网络路径用 `sites[].file`。
对外入口一律收 `{slug?, file?}`（`main.ts::findBook`），**给了 file 就按 file 精确取**；
三段键 `{repo}::{bookSlug}::{id}` 用作节点 id 与索引键。

### 19. Windows 下 `subprocess` 调 `npx` / `npm` 直接 FileNotFound

`subprocess.run(["npx", "tsc", ...])` 在 Git Bash 里能跑，在 Python 的 `CreateProcess` 里不行——
它们是 `npx.cmd`，不带扩展名不匹配。自检脚本因此每条命令先过一遍 `shutil.which`〔B3〕。

处理：`exe = shutil.which(cmd[0]) or cmd[0]`（`tools/selfcheck.py:39`）。
同时传 `env={**os.environ, "PYTHONIOENCODING": "utf-8"}`，否则子进程打印中文会 `UnicodeEncodeError`（cp936 控制台）。

### 20. 「成品 HTML 正文」的长度阈值要按渲染后文本量算

自检要选一份够长的 degraded 样本来验「HTML 直注入不被 markdown-it 二次处理」。
直接拿 `len(body) > 600` 判会**永远选不上**：成品 HTML 里标签占大头，可见文本远小于原始串〔B3〕。

处理：先 `re.sub(r"<[^>]+>", " ", body)` + `html.unescape` + 折叠空白，再比长度（`selfcheck.py:71`）。
反向同坑：探针里拿渲染后的 `innerText` 去和原始 HTML 串比长度，也是基准不一致——比较前先归到同一侧。

### 21. headless 帧率不受 vsync 封顶，165fps 不是 bug

帧率判据写「≥45」，无头 Edge 里测到 **165**〔B3：`_work/selfcheck-report.json`〕。
rAF 在无头模式不等合成器，所以这个数只能证明「没掉到阈值以下」，不能当真实 60Hz 屏的观感。

处理：判据保留下限语义（防卡死），把采样窗口（10s）与视口（1440×900）写进报告；
真实负载靠 `triangles()` 兜——大厅 **1,398**、数学房间 **3,874**（265 立柱 + 398 光点 + 45 展台）〔B3〕，
量级远低于阈值，不必怀疑帧率数字本身。

### 22. 地面学科名的可读性是四件事叠出来的

走廊地面文字做成 canvas texture 贴地网格，从大厅看**六条里只有四条认得全**，另两条被斜视角压扁〔B3：
`_work/shots-batch3/`〕。四个独立成因，缺一个都不清晰：

| 成因 | 处理 | 位置 |
|---|---|---|
| 雾把远处混成背景色 | `Fog` 的 near/far 收到 560/1300，覆盖最远走廊 | `scene3d.ts:96` |
| 与地面网格共面被挡 | 贴图抬高到 y=0.62，`transparent` + `opacity 0.92` + `DoubleSide` | `scene3d.ts:251` |
| 斜视角采样糊 | `tex.anisotropy = 4`，字号 96px，`shadowBlur 18` 描边提对比 | `scene3d.ts:239` |
| 文字方向读反 | 按大厅相机「屏幕左→右」取阅读侧，`rotation.order='YXZ'` 后再 atan2 | `scene3d.ts:225` |

排查顺序别搞反：**先单独拍一张再判读**，不要在截图里靠猜。`viewCorridor(key)` 把相机推进该走廊、
`corridorScreenBox(key)` 给出投影包围盒，两者配合即可逐条留证；
能看见却读不出=字号/各向异性，完全看不见=雾或高度。

判据只要求「走廊上有可读学科名」，**大厅视角 4/6 可辨 + 逐走廊 6/6 可辨**即达标，
不为了最后两条把 fov 改窄（改了会撞判据里的无溢出与帧率项）。

### 23. `stats-only` 档在库里是空的，只能造样本走一遍

`contentLevels` 实测 `{full: 128, degraded: 1, stats-only: 0}`〔X〕——判据要求「三档分流都有行为」，
但第三档**没有任何一本书可以点开**。若因此删掉这一支，等于把 schema 里存在的档位当死代码；
若在 `data/` 里改一本书的档位来凑样本，直接违反铁律「不改动 data 让演示好看」。

处理：把样本造在**调用侧**、不落库——`main.ts` 的诊断接口给 `openStatsOnlySample({slug?,file?})`，
取真实记录后在内存里把 `contentLevel` 覆成 `'stats-only'` 再走同一条 `openBook()`。

这是所有「schema 有、库里无」档位的通用验法：**造样本改的是传入参数，不是磁盘数据**。

### 24. grid 项的自动最小尺寸是 min-content，一条中文长标题能把弹层撑破 390

`width: min(660px, 100%)` 也压不住它。

处理：容器与每一条子项都显式 `min-width: 0`，长文本再配 `overflow-wrap: anywhere`
（`src/styles.css` 的 `#search-box` / `#search-line` / `#search-scope` / `#search-results` / `#search-status`）。
判据要量两层：`doc === 390` 和**弹层盒子 `right ≤ 390`**，只查前者会漏。〔K〕

### 25. 中文「单字 + 二字」分词天然高召回，无结果态验不出来

### 34. 「拷贝收敛」的三条前提，实测有一条是假的

前置清单写「`dist/` 24MB 里 16.7MB 是数据整份拷贝」，潜台词是这些拷贝可以删。逐族用浏览器实测运行期请求
（`_work/measure_data_requests.mjs`，结论落 `_work/measure-requests.json`）：

| 数据族 | 源体积 | 运行期请求 | 能不能删 |
|---|---|---|---|
| `bodies/` | 7.42 MiB | 129 本按需取 | 不能（判据 C1） |
| `sites/` | 3.72 MiB | 55 次 / 去重 54 本 | 不能——任务书给的条件是「若运行期零请求才可删」，实测非零 |
| `dist/`（结构 + 检索） | 4.61 MiB | 结构 5 片 + 检索 6 片全被取 | 不能 |
| `manifest.json` | 0.05 MiB | 3 次 | 不能 |
| `_report.json` + `raw/` | 0.02 MiB | **0** | 能，已不拷 |

也就是说纯靠「少拷」最多省 0.02 MiB，60% 的门槛根本够不着。〔K〕
处理：**功能全留，改传输形态**——构建期 gzip、客户端 `DecompressionStream` 还原，数据族 15.75 MiB → 4.58 MiB；
剩下的是 mermaid 裁剪 1.8 MiB。两条加起来 22.83 → 9.85 MiB（43.1%）。
教训：前置清单给的「死重」是估计值，收敛前先测请求再定删；不测就动手会先删出 bug 再发现删错了。

### 35. `.json.gz` 一进产物，门槛脚本自己先瞎了

三处脚本原本按明文 `.json` 认数据，换成 `.gz` 后都是**静默失效**（不报错、只是看不见）：

- `check_offline.py`：`.gz` 既不在 `CODE_EXTS` 也不满足 `suffix == '.json'`，直接跳出扫描范围——269 个数据文件
  会从「已扫」变成「不存在」，离线体检的覆盖率说降就降。改成先验 magic 再 `gzip.decompress` 后扫，报告里另打
  「预压 .gz 透明解压后扫描 269 个」，让覆盖率可核对。〔K〕
- `selfcheck.py::bundle_evidence()`：分片大小按 `search-<area>.json` 取，取不到就是 `None` → 「六片齐」判据直接红。
  改成 `.json.gz` / `.json` 两种都认（dev 态仍是明文），并把实际后缀记进 `shardSuffix`。
- `selfcheck_probe.mjs`：路由写的是 `'**/dist/search-*.json'`，`*.json` 要求以 `.json` 收尾，`.json.gz` 不匹配，
  「索引加载中」那条 600ms 延迟注入的断言会验不到 loading 态。改成 `'**/dist/search-*'`。〔K〕

### 36. 托管层可能替浏览器把 `.gz` 解压完

若服务对 `.gz` 加了 `Content-Encoding: gzip`，`res.arrayBuffer()` 拿到的是**已解压的明文 JSON**，
再喂给 `DecompressionStream` 必抛。反过来若服务开了 **SPA 回落**，取不到的分片会以 `200 + text/html` 返回，
`res.ok` 判不出来，`JSON.parse` 只给一句「Unexpected token '<'」。

处理都在 `src/data.ts`：`gunzip` 先看前两字节是不是 `1f 8b`，不是就按明文走；`getJson` 见到 `content-type: text/html`
就抛「拿到的是 HTML（产物缺这个文件）」——把「缺文件」和「解压失败」两种病因分开，别再混成一条 parse error。〔K〕
这类判定只在**系统边界**（外部托管行为）做，内部数据不做防御性校验。

### 37. mermaid 保留哪 5 类不等于只留 5 个分包

图型分包和布局分包是两套注册表。`flowchart` 在 mermaid 12 里默认走 **elk**（1.45 MiB，产物里最大单文件），
`mindmap` 走 cose-bilkent，兜底 `LAST_RESORT_LAYOUT` 才是 dagre。所以「只留 5 类」落地成 14 片 / 3.2 MiB
（闭包含共享的 `katex`、`sizeCapture`、`bpmnIcons`），不是 5 片。〔K〕

库里没有一处围栏用 frontmatter 覆写布局，`swimlane` 布局包（120 KB，库里 0 处使用）因此可安全剔除——
`getRegisteredLayoutAlgorithm` 自己会回落。反过来说：**没有实测就不能剔 elk**，把 flowchart 改成 dagre 是视觉行为变更，
不属于打包收敛。

### 38. `publicDir` 一刀切换成 `false`，dev 就看不到数据了

`publicDir: false` 能把整份 `data/` 从产物里摘掉，但 dev 也一起没了——`npm run dev` 时所有数据请求 404，

build 走 `zhishu:ship-data` 精挑 + 预压。代价是 dev 与产物形态不同（明文 vs `.gz`），由 `import.meta.env.PROD`
在 `dataUrl()` 一处对齐，两边都不用改调用点。〔K〕

### 39. 设了 `PCFSoftShadowMap` 却 census 报 `PCFShadowMap`（批 7）

three r186 起 `PCFSoftShadowMap` 被移除：`WebGLShadowMap` 首次渲染阴影时打一条
`warn('PCFSoftShadowMap has been removed. Using PCFShadowMap instead.')` 并把 `type` 归一成 `PCFShadowMap`。
所以「读回来的类型」永远不等于「你设的类型」，断言直接写 `type === 'PCFSoftShadowMap'` 必红。

处理：赋值照旧写 Soft（表达意图，旧版本仍生效），census 另记 `shadow.requested`，
断言拆成「有效类型含 PCF」+「requested === PCFSoftShadowMap」两条。
这条 warn 不进「控制台零报错」口径——探针只收 `m.type() === 'error'`，别把它误当失败去改代码。

### 40. 阴影明明开着，截图里却看不见（批 7）

不是 shadowMap 的问题，是**主光俯角**。方向光架到 `half*1.5` 高（约 60°）时，柱子影子几乎全压在自己背后，
关/开阴影的整屏亮度差只有 1.6e-4——肉眼和统计都等于没投影。降到 `half*0.8`（约 38°）后影子拖到展台上，
房间中段亮度差涨到 7.2e-3（45 倍）。

处理：取证要用亮度对照而不是「看着有影子」。A/B 采样区域选**受影面**而不是整屏，
且阈值至少留 2 倍余量（1.6e-4 贴 1e-4 门槛的写法会随机红）。

### 41. 阴影关了之后三角面「少了一半」（批 7）

`shadowMap.autoUpdate=false`（静态场景只烘一次）之后，`renderer.info.render.triangles` 每帧不再包含阴影 pass 的提交量，
数字会掉到只算主渲染。别以为掉帧数是 bug，也不能拿它当「总负载」报给 15 万预算判据。

处理：census 分三档报——`mainPass`（主渲染静态量）、`shadowPass`（投影体提交量）、`perFrame`（实际整帧），
判据按 `perFrame`，另加一条 `shadowPass > 0` 证明阴影 pass 真在跑。
透明 + `DoubleSide` 的材质主渲染会提交两遍，静态量与 GPU 读数对不上时先查这个（大厅静态 810 vs 读数 1,398 即此因）。

### 42. Bloom 一开帧率掉 10% 以上（批 7）

`UnrealBloomPass` 默认按 `renderer` 的全分辨率建 mip 链，DPR=2 时是 4 倍像素量。

处理：`composer.setSize()` **之后**再 `bloomPass.setSize(w*pr*0.65, h*pr*0.65)`——composer 在 render 时不会替 pass 重算尺寸，
所以这个 0.65 会一直生效。省回 ~11% 帧时，肉眼在 1440×900 上看不出高光边缘差别。
同理 `composer.setPixelRatio(renderer.getPixelRatio())` 必须显式调，否则 composer 用默认 1，DPR>1 的机器上后期链会糊。

### 43. 房间点光在地面留一块过曝热点（批 4 之后批 7 复现）

`decay=2` 的 PointLight 挂在 y=7 时，离地面太近，中心照度 ≈ intensity/d² 直接爆。抬到 y=18、强度 420（后调 392）热点消失。

处理：房间补光一律挂到展台以上；判亮度别看整屏 mean，要按 `sampleLuminance` 采地面横带——
整屏 mean 被天空带稀释，地面过曝在整屏上只体现为 +0.02。

### 44. 光点做了 GPU billboard 之后点不中（批 7）

把朝向塞进顶点着色器（`modelViewMatrix` 提旋转）确实省掉每帧重写实例矩阵，但 `InstancedMesh.raycast`
读的是**实例矩阵**，着色器里的旋转对拾取不可见——射线命中的还是那根竖着的 1×1 面片，398 个光点全部点偏。

处理：billboard 放 CPU 侧，每帧 `matrix.compose(pos, camera.quaternion, scale)` 重写实例矩阵；
断言看 `dotBillboard === true` 与贴图指纹 `canvas:radial-gradient-64`，不看帧率。

### 45. headless 里 PMREM 环境光「看不出有没有生效」（批 7）

envMap 只抬高光与金属感，截图亮度差在噪声里；而 headless 的 ANGLE 驱动偶尔不给浮点 render target。

处理：断言走**指纹**而不是像素——`scene.environment` 非空 + `isRenderTargetTexture` + `halfFloat` +

### 46. 书脊特写读不出书名：先怀疑朝向，别急着加分辨率（批 8）

首版 1024² 图集、每格 32×160，特写里书名糊成竖纹。第一反应是「格子太小」，
于是把图集提到 2048²/64×320（每格像素密度 4 倍）——**截图一个像素都没变**。

处理：取证先把「图集里到底画了什么」dump 出来看：`spineCellPeek(i)` 按 UV 反算出该格的像素矩形，
从 `atlas.textures[page].image` 裁出来 4× 近邻放大成 dataURL，同时回报格像素尺寸、世界尺寸、屏幕上尺寸与倍率。
读到 `magnify 0.22`（原生像素是屏幕像素的 4.5 倍）就知道分辨率从来不是瓶颈，问题在几何把贴图怎么贴。
判据类问题（「特写里书名可读」）必须先定位是内容错还是呈现错，否则会白加一档显存。

### 47. `GeoBuilder.quad` 修绕序时换了顶点没换 UV → 贴图转置 90°（批 8）

quad 的入参顺序是 a→b→c / a→c→d，若给定的 b、d 使绕序与法线相反，就交换 b、d 来翻绕序。
UV 是按 `[u0,v0][u1,v0][u1,v1][u0,v1]` 绑到**槽位**的，交换顶点后 UV 仍留在原槽位——贴图被转置 90°。
书脊格是 1:5 的竖长条，转置后书名横躺、金色横线变竖纹，看起来就是「糊」。

处理：UV 绑**角点**而不是绑槽位——交换 b、d 时把它们的 uv 一起交换。
凡是「运行时可能翻绕序」的通用 quad 构造器都要按这条写，别留给调用方对齐。

### 48. 三面墙的书脊，朝外那面的数字是镜像的（批 8）

修完转置仍读不出书名：正对北墙是好的，南墙那排的书名铜牌数字变 `Ɛ`、汉字左右翻。
原因是面内水平轴直接取了书架行的 `dir`。书架沿左/右/后三面墙排布，
`dir` 与墙面法线构成的**手性**在对侧墙是反的，同一套 UV 映射到两种手性基上，其中一面必然镜像。

处理：面内水平轴由法线推出，`u = up × normal`，不引用行方向。
判据不是「截图看着正」，而是**逐墙对账**：同一条书脊在四面墙上的 UV 递增方向必须与 `normal` 右手一致。

### 49. 合并几何之后拾取只剩 `faceIndex`，线性查表会在点击时卡一帧（批 8）

`BufferGeometry` 合并成一区 1–3 个 Mesh 后，`Raycaster` 返回的是整块几何的三角下标，
不再带实例号。若点击时再遍历「这条脊覆盖哪些三角形」，一次点击要做几万次数学，掉帧且难复现。

处理：建脊时按写入顺序同步落三张逐三角形表——`triRole`（章格/铜牌/封面）、`triSlot`（书位）、
`triChapter`（章序），另建 `triSpine`（每条脊 = 6 面 × 2 三角 = 12 个下标 → 书脊序号）。
拾取是 `triSpine[faceIndex]` 一次数组寻址。门槛断言查 `mapLengths === 12 × cells`，
再加一条「映射表答案 === 真实射线答案」的特写对账（批 8 取 15 条脊全对）。

### 50. 切区释放贴图，大厅门楣牌匾跟着变黑块（批 8）

`clearRoom()` 里对 `atlas.textures` 与 `roomMats` 逐个 `dispose()` 是对的，
但区名牌匾纹理是**大厅门外楣与本区门内共用同一张**（`plaqueFor()` 缓存、一次生成不重建）。
顺手写成「释放本区所有用到的纹理」，回大厅后六块牌匾与地面铭牌就是六个黑块。

处理：释放清单只列**本区独占**的资源（图集页、本区新建材质与几何）；
共享纹理挂在实例级 `Map` 上，随场景销毁才 dispose。判据：切区来回三轮后
`census().labels.plaqueTextures === 6 && nameplateTextures === 6`，且大厅截图牌匾非纯色块。

### 51. 六区点光放在房间中心，大厅俯视是六个黑盒子（批 8）

批 8 给每区加了屋顶与四壁。区光还留在房间几何中心时，箱体六面法线**全部背灯**，
`MeshStandardMaterial` 受光为 0——大厅里看六个体量就是六个纯黑方块，只剩门缝漏光。

处理：区光抬到屋顶上方（`ROOM_HEIGHT + 16`）当「轮廓灯」用，室内另有自己的两盏点光。
顺带一条同源教训：灯光的挂载父级决定它进不进某视图的受光集合（批 7 靠把区光挪出房间拿回 13 fps），
`scene.children` 里的灯永远参与着色，分组隐藏不会让灯消失。

### 52. 雾是「视图参数」不是「场景常量」（批 8）

大厅体量缩小后按老机位 (0,330,380) 拍，画面只剩一角；把机位拉近到 (0,232,264) 反而整幅发灰——
`Fog(210, 620)` 是按室内距离定的，相机到八角厅约 505 单位已进雾带，72% 的像素被糊成背景色。

处理：`HALL_FOG = (420,1500)` 与 `ROOM_FOG = (210,620)` 两套，随 `showHall/enterRoom` 切；
`census().fog` 回报当前生效值，别在断言里写死一组数字。
判据「大厅看得见八角形与六扇门」是构图问题，先查相机与雾，再查几何。

### 53. `controls.minDistance` 会把脚本化的特写静默夹住（批 8）

`focusSpine(i, 0.55)` 与 `focusSpine(i, 2.6)` 截出同一张图：OrbitControls 每帧把距离夹回 `minDistance = 3.2`，
不报错也不回传实际值。取证脚本据此以为「贴到 0.55 也读不出字」，把结论记错了方向。

处理：特写一律按夹后的 3.2 拍，并在探针里回传 `focusSpine` 的实际机位距离；
要么显式临时下调 `minDistance`，要么在报告里注明有效距离。任何「程序化摆相机」的取证都要读回最终位姿。

### 54. 三角面 6.2k、draw call 29，帧率却只有 40：这时减几何一点用都没有（批 8）

室内机位把墙面、地板、书架整片送进片元着色，瓶颈从几何变成填充率。
逐角色 `roleHide` 归因：藏书架 +8.6 fps、藏墙 +4.9、藏地板 +3.0、藏书脊 **0.4**——
最贵的是「大面积的素面」，而书脊（本批的主角）几乎不要钱。

处理：`renderScale = 0.85` 只用于室内视图（帧缓冲按面积缩到 72%，输出仍铺满画布由 GPU 放大），
实测三区 40.5→55.7 / 39.7→52.3 / 53→67，书脊格仍有 3.8 倍像素余量、特写读得出书名。
反例记录：把墙面材质从 Standard 换成 **Lambert 反而慢 2–3 fps**（五区同向，已回退），
图集与结构贴图的 `anisotropy` 从 4 降到 1 则完全无变化——所以别照搬「换便宜着色器」的直觉，
先用 `roleHide` + 成对 A/B（同一次会话里开关对照）测，跨轮次的绝对值噪声有 ±2 fps。

### 55. 进区机位按世界 +Z 摆，六个区里只有一个是室内（批 8）

批 7 的机位是 `center + (0, h, side*0.95)`——那时候房间是悬浮圆盘阵列，没有朝向，摆哪边都一样。
批 8 房间绕 Y 转了 `π/2 − angle`（正门恒朝走廊），本地 −Z 才是门墙那侧；
继续用世界 +Z 偏移，等于把相机塞进另外五个区的后墙书架里。
症状很迷惑：截图不是黑屏也不是白屏，而是**一整幅横板纹理**，看起来像「墙没建起来」，
实际是相机在墙内、看到的是墙的内侧面 30 单位外的另一面。
指标全绿（tris/calls/fps/拾取都对），只有截图能看出来——所以室内机位必须出图检查，不能只看数。

处理：`toDoor = (-cos angle, 0, -sin angle)`，`eye = center + toDoor * side * 0.3`。
这条向量的符号可以直接推：本地 (0,0,-1) 经 `Ry(π/2 − angle)` 得到 `(-cos, 0, -sin)`，与门墙同侧。

### 56. `GeoBuilder.tri` 声明了法线却没修绕序 → 大厅地面总览图整块被背面剔除（批 8）

`quad()` 早就按「几何绕序必须与声明法线一致」做了自动翻面，`tri()` 是后来补的，只写了法线没修绕序。
八角厅地面用 `tri(..., UP)` 铺，绕序实际让几何法线朝下；墙面是 FrontSide，于是
**总览图（贴在地面上的 emissiveMap）整块不可见**，而三角面数、draw call、贴图张数全部正常。
判据：`roleHide('hallFloor')` 前后 `sampleLuminance` 逐字节相同——藏掉一个「画面上明摆着占 40% 面积」的
物体而像素不动，只能是它根本没被画。修 `tri()` 时 UV 要跟着顶点一起换（角点绑定，不是槽位绑定），
否则修好可见性又引入 90° 转置（同 47）。

### 57. 走廊壳体写成 DoubleSide，取证机位怎么摆都读不出地面铭牌（批 8）

走廊是带顶的管子：侧墙法线朝中线、顶面法线朝下，本来靠 FrontSide 做「娃娃屋」——
俯视时顶面被剔除、露出地面和铭牌。材质却写成 DoubleSide，顶面从上方照样画，
于是侧视读到的是远侧墙糊满画面、俯视读到的是封闭暗管盖，两种机位都拍不到地上的字。
连着犯了两个错：先按错误的直觉摆侧视机位，再怀疑铭牌没建出来。
判据是 `roleHide('corridorName')` 前后亮度**完全不变**——贴图与网格都在，只是被顶面挡住了。
处理：壳体回 FrontSide；侧视机位的锚点取 `mesh.position` 而不是按 `spec.at` 比例猜房间半径
（猜出来的点落在相机脚下，铭牌整条糊出画面），左右两侧由文字基线的 `flip` 决定，
否则左半区的字是反的。六区投影宽高比 11–17，门槛取 ≥3。

### 58. `applyLod` 每帧重写可见性，`roleHide` 对书脊和光尘永远读出 0（批 8）

用 `roleHide('spines', true)` 做归因时：返回 n=2、三角面数不变、截图不变，看起来像 roleHide 坏了。
实际是 `applyLod()` 每帧执行 `mesh.visible = dist <= 240`，把隐藏下一帧就改回去。
光尘同理（`dist <= 52`）。所以**凡是 LOD 管辖的角色，roleHide 只能证明「它归 LOD 管」，不能做归因**；
要归因这类物体得先停掉 `applyLod` 或临时把阈值改成 0。
其余角色（墙、书架、天花、地板、走廊）不受影响，照旧可用。

### 59. 一盏放在房间中轴线的点光，把正对机位的书架墙打曝（批 8）

批 7 的书脊是弧形圆盘，同一盏 210 的点光在上面摊成一条渐变；批 8 变成一整面平书架墙后，
点光在这面墙上的**垂足**（x=灯的水平位置、y=灯的高度）是一块正对相机、法线正对灯的高照度区，
整片直接过曝：亮度采样 mean 0.80、`brightRatio` 0.60，画面上就是一个「恰好一个书格宽」的白块。
排查过程值得记：换 Bloom 阈值（0.6→1.0）只降 0.05，说明不是辉光；把书脊材质改成哑光
（roughness 0.82 / metalness 0.02）反而更亮（0.64→0.79），说明不是镜面；
只有降灯强才动得了——但灯降到不曝（≤50）时特写就黑成 0.02，书名读不出。
处理：灯沿走道两侧摆（`x = ±side*0.34`），正对机位的远墙只吃斜射；侧墙虽然仍是垂足面，
但它在画面里近乎侧视、光斑被投影拉散。强度保持批 7 的 210/74 不动，
实测热区 mean 0.16、`brightRatio` 0，特写亮度与书名可读性不变。

### 60. 三面书架在房间转角互相穿插，端头那本书种进了邻墙（批 8）

`rows` 沿墙参数 `u ∈ [-tierLen/2, +tierLen/2]`，而 `tierLen = side - 2.6` 只留了一个层板厚。
左墙书架占 `x ∈ [-side/2, -side/2 + SHELF_DEPTH]`，背墙书架占 `z ∈ [side/2 - SHELF_DEPTH, side/2]`：
只要 `SHELF_DEPTH > 1.3`（实测 2.6），两条书排在角上就重叠出一个 `(SHELF_DEPTH-1.3)²` 的公共方块，
最靠端头的几册书整个塞进邻墙书架内部——3D 里是穿模，2D 里是两点重叠、点击命中错书。
判据不能只看截图：2D 降级视图里逐个数 `g[data-slug]` 的 `getBoundingClientRect()` 中心，
对中心做一次 `elementFromPoint`，凡是「命中元素所属的书位 ≠ 被量的书位」就是重叠区——
数学区实测 45 个书位里端头几个全中，比盯 3D 角落快得多。处理是两端各让出一个进深
（`corner = SHELF_DEPTH + 0.2`，`tierLen = side - 2*corner`），
并把 `side` 的 `+3` 余量换成 `+2*corner`：每面墙的书排短 3.0 单位，房间只在装不下的区才变宽
（实测边长数学 20 → 20 不变、AI 23 → 26；主口径三角面 math 6,158 不变、chem 2,774 → 2,666 属光尘按距离分档的可见性差异）。
**别只改 `tierLen` 不改 `side`**：那等于白白扔掉两面墙各一个进深的容量，超载区会被贪心摊得更密。

### 61. 2D 平面投影把六层书架压成一条线，`locator.click()` 永远等不到「元素接收事件」（批 8）

俯视平面没有第三维，同一面墙的 6 层书位投到同一条 `x` 上，后画的那本盖住先画的——
这是投影本身的性质，不是布局 bug（3D 里它们分层，互不重叠）。
但它会让门槛卡死：Playwright 的动作性检查要求「点击点命中该元素自身」，
而首个书位的中心命中到的是压在上面那层的兄弟 `<g>`，于是 `locator('svg g[data-slug]').first().click()`
一直停在 "waiting for locator"——`count()` 有 45、`isVisible()` 为真、`elementFromPoint` 也拿得到东西，
看着像选择器或渲染问题，实际是被覆盖。
处理：探针改用 `boundingRect` 中心 + `document.elementFromPoint(...).closest('svg g[data-slug]')`
自己筛出**第一个中心能命中本体的书位**，再 `touchscreen.tap(x, y)`——触屏降级本来就该走指点头。
断言也随之变强：不只验「开了正文」，还验「开的是点到的那一本」（`readerState().book === 命中 g.dataset.slug`）。
顺带一个真 bug：章数标注 `<text>` 比书位宽（0.42–0.72 世界单位 vs 两位数约 0.9），
它原本参与命中、会替邻书接单——标注组一律 `pointer-events: none`。

### 62. 删掉降级分支以后，残留的选择器把「路径已删」读成「渲染失败」（批 9）

`src/svg2d.ts` 一删，`#svg-root`、`.flat-*`、`els.flat`、`?flat=1` 这些名字在源码里没了，
但探针与取证脚本还在按老口径读它们，于是出现两种**方向相反**的假信号：

- **假失败**：旧判据「降级视图无 WebGL 画布、SVG 成图」读 `#svg-root svg`，节点没了 → 判据红。
  这不是回归，是判据在描述一条已经不存在的支路。处理不是删掉它，而是**反写成 3D 语义**再留档
  （现在这条读的是 `mode === 'three'` + `#three-root canvas` 有像素 + 画面非全黑），
  断言总数只增不减，`SPACE_ASSERT_MIN` 从 89 提到 98。
- **假通过**：反写成 `document.querySelector('#svg-root') === null` 也是绿的——它只证明 DOM 里没这个节点，
  不证明 3D 活着。任何「删了 X 所以 X 不存在」式的判据都是空判据，必须配一条正向的「Y 确实在工作」。

另外两处残留不会报错但会骗人：`index.html` 里删掉 `#svg-root` 后，SVG 专用 CSS 还在（无害但会误导下一个读代码的人）；
取证脚本里的 `?flat=1` 参数在 `main.ts` 不再读它之后**静默失效**——截图看起来是 3D，脚本注释却写着「平面视图」，
这批就是靠这个发现 mobile 取证图其实早换成 3D 了。收尾做法：删分支之后
`grep -rn "svg2d|MatrixFlat|flat=1|prefersFlatView|#svg-root"` 全仓过一遍，
命中的每一处要么删干净、要么改成新语义，不留「读起来像还在」的字符串。

### 63. 手指拖视角，顺手把书翻开了（批 9 B3）

触屏上 `pointerdown → pointermove → pointerup` 之后浏览器还会补发一个合成 `click`，只要位移没超过平台的判定线；
我们自己的 `handleClick` 又没看位移量，于是「划一下 11px」既转了视角又开了一本书。两个坑叠在一起：

1. **位移量只按首末两点算不够**。手指画个「出去再回来」的弧，首末距离是 0，但中途走了十几像素，视角确实被拖动了。
   `tapVerdict()` 取的是整段序列里离起点的**最大**距离。
2. **容忍值不能与鼠标共用一个数**。鼠标 6px 合适，手指抖动大，任务书 B3 又钉了「≥8px 必须判拖拽」，
   所以 `TAP_SLOP_TOUCH = 8` / `TAP_SLOP_MOUSE = 6` 两个常量分开，阈值按「大于等于即判拖拽」写，8px 那一格也算拖。

判据用 CDP `Input.dispatchTouchEvent` 打真实序列（touchStart → 两次 touchMove → touchEnd），
不是往 DOM 派发自定义事件；读 `lastTap()` 的 `{kind:'touch', action:'drag', moved:17, slop:8}`，
再比 `readerState()` 与滑动前逐字段一致。轻点那一支同样要验「开的是点到的那一本那一章」，
`faceIndex` 反查表与实时射线各跑一次对账（批 8 的映射表在这条上继续当唯一真源，不补第二次射线拾取）。

### 64. 窄屏的 bloom + DPR + 光尘三样叠起来吃 fillrate，但 headless 帧率探针测不出差别（批 9 B2）

结构上这三样在窄屏最贵：`deviceScaleFactor 2` 下 390×844 是 780×1688 ≈ 1.32 Mpx/帧；
UnrealBloomPass 要在这个分辨率上做 5 级 mip 的可分离模糊再加法合成；光尘是大面积加法混合 quad。
所以 `qualityTier()` 的 mobile 档把 dpr 压到 1.5、bloom 与阴影整档关掉、光尘预算 220、帧缓冲 0.72。

但**别拿 fps 当这条的证据**。四个组合（现行档 / 只开 bloom / 只把帧缓冲拉回 1.0 / 两样都改）
在 390×844 各测 4 秒，报出来的数一模一样：大厅 165.1–165.2、数学区 140.7——
headless 的 rAF 采样在这一档上直接饱和在 ~165，帧时间还剩大把余量，降不降档看不出来。
同机位在桌面 1440×900 就灵敏（批 9 C1 试那盏自下而上的补顶灯时实测 62.1 → 165.2 fps，2.7× 帧时），
说明采样器没问题，是窄屏本来就跑不满。

两个后果写进了门槛口径：

- 「390 帧率 ≥30」只当**回归底线**（真炸了能兜住），不当画质档的成效证明；
- 画质档由 `quality()` 逐项读开关来断言（`name / dprCap / pixelRatio / shadows / bloom / bloomScale / renderScale / dustBudget`），
  实测 `{"name":"mobile","dprCap":1.5,"pixelRatio":1.5,"shadows":false,"bloom":false,"renderScale":0.72,"dustBudget":220}`。

还有个连带的假信号：`setPassEnabled('Bloom', true)` 在 bloom 没建的档上是**空操作**
（`postList` 里找不到就 `return false`），而它的返回值没人看——A/B 脚本因此一度以为「bloom 开了但没差别」。
用运行时开关反证画质档之前，先读返回值。

### 65. 藻井、檐口、门洞上沿、阅览室天花的法线全部朝下，方向光永远打不动它们（批 9 C1）

这些面都是「从里往外看」的顶面，法线 −Y。`DirectionalLight` / `PointLight` 的漫反射项是 `max(0, dot(N, L))`，
从上方来的光对朝下的面 dot < 0，被 clamp 成 0——**不是不够亮，是恒等于零**。
`HemisphereLight` 是唯一能照亮它们的标准灯：朝下的法线取的是**地面色**那一路，权重 0.5·dotNL+0.5，
所以 C1 的杠杆是「抬地面色 + 抬强度」，不是加灯。

中途确实加过一盏自下而上的 `DirectionalLight` 补顶面，代价实测 2.7× 帧时（大厅同机位 8 秒采样 62.1 → 165.2 fps），
收益只有整帧 p95 0.06497 → 0.08002，撤了。顶面最后走的是「把反弹烤进表面」这条路：
墙面 / 天花 / 横梁三张程序化贴图各配一份 `emissive + emissiveMap`（暖白 `0xffe9c9`，强度 0.11 / 0.22 / 0.16），
零逐片元成本，等价于补了一盏不花钱的灯。

顺带两个读数陷阱，都在这条上踩过：

- **只抬反照率抬不动暗部**。墙面基色从 `#2f2620` 提到 `#3d3026`（1.7×），整帧亮度只动了几个百分点——
  ACES（Narkowicz 近似）+ sRGB 编码在 toe 段把差异压掉了。要么改辐照度，要么走 emissive。
- **`HemisphereLight` 的 ground 色同时喂给整个场景的朝下面**，抬它等于抬地板、书脊底、桌下，不只有天花。
  所以它是「一根杠杆拉一片」，调完必须回头看书脊反差有没有被顶掉（本批 min 15.21，判据线 4.5，没动）。

### 66. 亮度采样窗落在 DOM 头部条上，`readPixels` 的原点又在左下角（批 9 C1）

为了回答「天花到底画没画」，先用 `sampleLuminance` 取画面顶部 6% 的条带，结果三个机位取到的数一模一样，
一度得出「天花没被画出来」的错误结论。两处口径叠着坑人：

1. WebGL `readPixels` 的原点在**左下**，归一化窗口取的是图像上沿还是下沿，取决于实现里翻不翻 Y——
   不核对就会拿错半幅。
2. 1440×900 的画面顶部约 55px 是 DOM 的头部条（`#topbar`），不是 WebGL 画布内容。canvas 里那块是空的或背景色，
   于是「顶带亮度」测的是 UI，不是场景。

判据改成先确认窗口落在画布几何内（按 `#three-root` 的 rect 换算），再用逐角色对照：
`roleHide('ceiling')` 前后三角面 8,494 → 8,492、`roleHide('wall')` → 8,482，证明它们**在画**、只是黑，
方向这才转到辐照度上（见 65）。另外「隐藏某角色后画面逐字节不变」也不能直接读成「该角色没画」——
它同样可能是被别的东西整个挡住，必须配三角面计数一起看。

### 67. 一次点击派两个钩子，两条异步链各发一次 `bookRecord`，面板从 chapter 飘回 overview（批 9）

点书脊的 chapter 命中原本这样派发：`onPickBook(...)` 紧接 `onPickChapter(...)`。
`main.pickBook` 与 `main.pickChapter` 各自 `bookRecord(book).then(...)`，而 `bookRecord` 只缓存**已完成**的记录、
不缓存进行中的 promise——同一本书未缓存时就是两次并发 fetch。两条链的尾巴分别是
`openBook()`（置 `mode='overview'`）和 `openBook()+openChapter()`（置 `mode='chapter'`），
谁后回来谁说了算：fetch 顺序一抖，`overview` 就把刚打开的章节页打回去。
桌面机位下书脊大、命中稳、缓存热，这条一直绿；390 竖屏第一次点就翻车（`mode:'overview'`，
但 `file` 是对的——所以「开对书」的判据没抓到它，得看 `mode`）。

修法在派发侧：chapter 命中只发 `onPickChapter`，`pickChapter` 自己已经做了
`setSelection + openBook + openChapter`，补发 `onPickBook` 纯属重复，顺带省掉一次 JSON 请求。
教训是通用的一条：**同一个用户手势不要派两条各自异步收尾的链**，
要么合并成一条，要么把被调方改成幂等 + 记忆化进行中的 promise。

### 68. 竖屏为了「把房间装全」把机位退到门外，装出来是娃娃屋，书脊也点不中（批 9 B1）

`fovForAspect` 把竖屏 fov 抬到 76 之后，`roomEye` 里那条「按水平视野解距离」仍然要求
`need = (side/2 + 1.2) / tan(halfFov)`：390×844 的 aspect 只有 0.462，水平半角 atan(tan38°×0.462) ≈ 20.3°，
side=20 的数学区解出 dist ≈ 23 单位——门墙在 10，等于相机退到门外 13 单位。
构图账上顶点全入画、判据全绿，截图却是一间摆在黑盒子里的小模型：画面上部三分之一是走廊与门洞，
书脊投影只剩 20px 上下，指头点上去落进书顶的铜牌带，开成「本书总览」。

结论是**判据本身写错了方向**：窄屏水平视野是物理限制，「两侧墙全进画」与「书脊点得中」不可兼得。
改成竖屏站门口看进去（`dist = side*0.5 − 1.5`，即门墙内侧 1.5 单位），两侧墙远段出画，
判据相应分组（`face` / `ceiling` / `floor` 三段各 4/4 算「有一间房」，`back` / `sidewall` 只作参考量），
「点得中」另用 `spineProbe().px ≥ 36` 把一条（实测 math 39–51、ai 23–33）。
桌面端那一档一字不动（`aspectRamp` 在 aspect ≥1 取 0，仍是批 8 的 `side*0.3` + fov 56），所以这条改动的回归面只在窄屏。

写判据时值得记住的两条：一是**别把「装得下」当「看得好」**，构图账要配一条可读性/可点性的量；
二是竖屏的 `ROOM_FOV_MIN` 一度也从 56 降到 52 想「更宽一点」，结果 `need` 随 tan 涨、相机被推出门外——
fov 与距离是一对耦合量，动一个必须重看另一个。

### 69. 「在画内」是布尔，「占屏多少」才是构图（批 10 A）

批 9 的窄屏判据数的是「20 个结构里几个入画」：全绿。可 390 实拍里大厅主体只占竖屏中段三分之一，
上下两条死黑带——因为 20 点全在画内与它们的**包络**占多少屏是两个量，前者对「贴边缩小」完全免疫。
批 10 把判据改成主体投影包络的竖向/横向占比（≥50% / ≥75%），外加底部 UI 净空（≤22% 高、≤10% 重叠）

否则渲染退化成贴边小图、断言照样全绿。

### 70. 题签做得和书脊一样宽，远看就是「蓝盒子上贴黑胶带」（批 10 C）

批 9 的暗底题签占满整条脊宽（100%），近看字口反差 15+，三米外却只剩一条黑带——反差是**局部**指标，

### 71. 竖屏退机位求「装全」，边缘留的不是黑边是全黑（批 10 A/B）

把相机退出八角壳外拉广角，壳外没有几何、没有光，四周整圈是 0.02 以下的纯黑；肉眼读作「画面缩成小方框」。

### 72. 八角壳的碰撞盒把 `yaw` 取成边方位角，六面墙变成六根径向鳍（批 11 B）

`hallBlockers` 里每面墙是一个 OBB：`hx = WALL_T/2`（薄）、`hz = 半弦长`（长），也就是说**长轴是本地 z**，
而本地 z 在世界里等于 `(sin yaw, cos yaw)`。当时按直觉写了 `yaw = a`（a 是这条边的方位角），
于是长轴变成 `(sin a, cos a)`，而切线方向算的是 `dir = (−sin a, cos a)`——两者只在 a = 0°/180° 时重合。
结果：八面里只有两面真的是墙，其余六面成了从墙中线戳向厅心的鳍。全周扫描实测 −135°（实心边）一路走到
130 单位没人拦，而 chem/tools 方向在 39.6 单位就被「墙」提前拦下。改成 `yaw = −a` 后：实心边 43.08 拦停、
门洞方向 131–136.68 通到门面。教训：**同一份几何里出现两个方向约定（`dir` 与 `yaw`）时，两者必须由同一个
向量反解出来，不能各写各的**；而「抽四个方向测碰撞」根本盖不住这类错——判据必须扫全周（本批 72 向）。

### 73. 正好相接的两块膨胀盒在转角留楔形缺口，最小穿透轴把人翻到墙外（批 11 B）

鳍修好之后 −157°、23° 这类「顶点方向」仍然漏：人在厅内，走到八角顶点处被推了一把，下一帧已经在壳外
（travelled 46.48 → 曾到 128）。根因不是步长穿透（步长 0.12，墙厚 1.2），而是推出方向按「当前在盒心的哪一侧」
算——薄墙斜着撞上去时，人在膨胀带里的那一小段恰好跨过了中线，符号翻到外侧，于是被**推过墙**而不是推回原路。
改法：`resolveSlide` 收一个 `prev`（本步起点），按**上一帧是从哪一根轴的外面进来**决定推回哪一面；
段与段再搭接 1.2 作补强。实测四向（−157/−135/0/23）全部 ≤46.5 拦停、travelled ≤46.46，无一翻出。
教训：**碰撞解算的「方向」不能由当前位置单独决定**，它必须由运动历史决定；否则同一坐标在墙的两边各有
一套合理解，选哪个是掷硬币。

### 74. 俯瞰总览图当漫游地面用，站到 1.65 眼高上就是一张糊白的地名图（批 11 F）

大厅地面在 orbit 下是「从天花板看下去的平面图」（六区名 + 连线），1024² 摊到 95 单位见方 =
**10.8 texel/单位**，再叠 `emissiveIntensity 0.9`。俯瞰时它小、且读的是内容，所以批 10 的判据全绿；
第一人称贴地看就变成一片带横纹的白斑。批 11 给漫游单做一套材质：canvas 石板图 256²、`repeat(14,14)`
→ 6.3 单位一瓦片、**37.6 texel/单位**，各向异性 8；墙面/天花/藻井/走廊壳做 clone + `emissiveMap = map`

### 75. `drawImage(webglCanvas)` 读回全黑，近景判据一度报「100% 纯黑」（批 11 F）

取证脚本用离屏 2D canvas 抄主画布算暗像素比，八个机位全部 dark 100%、hot 0%——画面明明是正常的。
根因：WebGL 上下文没开 `preserveDrawingBuffer`，合成后 drawing buffer 即被清，`drawImage` 只能拿到全零。

判据脚本要复用运行时的采样口，别在页面外面另起一套读图口径。

### 76. 准星对不准要读的那本书：沿排斜看时，凸出的邻本先挡住中心射线（批 11 C）

### 77. 「摇杆不压学科条」这条断言其实是恒真的（批 11 D）

断言写成读 `[data-stick]` 的 `getBoundingClientRect()` 与 `#roombar` 求交，跑完是绿的——但报告里那行
读数写着 `"stick": {"x":0,"y":0,"w":0,"h":0,"bottom":0,"hidden":true}`：**摇杆是「指头落下才出现」的**，

### 79. 展柜坐标取了 Vec3 的 y 分量，六座柜塌成一条线而碰撞盒是对的（批 12 B）

柜位 = 径向 × `caseR` + 内倾 × `caseLean`，写成了 `rad[1] * caseR + tan[1] * caseLean`：`rad/tan` 来自
单位向量 `(cos a, 0, sin a)`，索引 1 是**竖直分量、恒为 0**——x 正确、z 永远 0。结果六座柜全挤在 `z = 0`
这条线上，而碰撞盒另用 `cos/sin` 摆位是对的，于是**所见非所撞**：人绕着不存在的柜子走、直接穿过看得见的柜子。
实测六座全塌到 `z = 0` 这条线上（x ≈ 19·cos a，方位 90/270 那两座只剩 3.7 的半径，直接压在索引台上），
门槛「六座展柜落在内圈 18–22」当场报红；修完六座实测圈半径全等 **19.36**。

教训两条：① 手挑 `x/y/z` 下标时，凡三个分量里只用两个，就写成解构（`const { x, z } = v`）或整向量加乘；
② **可见几何与碰撞体必须各自被断言**——本批同时量「柜网格实测圈半径」与「`walkGapAt` 间隙」，
只断言一边就会放过这类错位（批 11 的 yaw 反向是同一族的另一半）。

### 80. 台面按六等分摆扇区，与六条走廊实际方位差到 45°（批 12 A）

六条走廊的方位不是均匀 60°，而是八角厅六面门所在的 **45 / 90 / 135 / 180 / 270 / 315**（225 那面是正门背面墙）。
按 `i * 60°` 分扇区，扇区中心线与门洞质心最大差 45°——「点台面这一区走过去」会撞在一面实墙上。

规则：**分界线取相邻两条走廊方位的角平分线**（`bis(other) = r.angle + normPi(other − r.angle) / 2`），
于是扇区中心线**恒等于**该区走廊方位（构造上 drift = 0），代价是六块扇区**宽度不等**（45° 与 67.5° 两种）。
门槛据此实测：门洞扫描得 6 段通孔 45/90/135/180/270/315、宽 17°，扇区中心线 vs 门洞质心角差 max **0.00°**；
边界判定改用**每区自己的 `a0/a1`** 往内 2°（仍是本区）与往外 2°（落进邻区），不再用固定 ±20.5/±24.5——
那种对称容差只在均匀扇区成立，第一版就是被它坑的：general / tools / chem / math 四区 ±24.5 都还在自己 67.5° 宽的
扇区里，断言恒真。教训：**不对称的划分不能用对称的判据量**。

### 81. `Raycaster` 不看 `visible`：隐藏的扇区高亮块把台面自己挡住了（批 12 D）

环视断言第一次只报 **4/8**，两个独立原因叠在一起：

1. 高亮楔块的角色名是 `deskSectorHl`，而 `sightTargets()` 的 skip 集写的是 `'sectorHl'`——差一个前缀等于没跳，
   这些静止 `visible:false` 的板仍在射线目标表里，把 deg 0 的读数压成 `wallDist 1.07` 并判「不是内容」。
   three 的 `Raycaster.intersectObject()` 只测 `layers`，**根本不测 `visible`**。
2. 展柜宽 3、圈半径 19，角宽只有 ±4.4°；站位一离心，柜中心就与 45° 网格差出 11–14°，单条水平射线从柜子侧面掠过。
   判据改成「8 个 45° 方位 × **±20° 视野带** × 俯仰扇 [0,−6,−12,−20,−30]」（人在这一个方向上是会扫视、会俯仰的），
   同一站立点 4/8 → **6/8**。

教训：**用射线做判据时目标表要按「画面上真存在的东西」显式构造**；角色名这类字符串在两个文件里各写一遍早晚漂——
读数里出现空 `role` 或短得离谱的 `wallDist` 时，先怀疑 skip 集与命名，而不是先怀疑场景。

### 82. 台面自发光 + 贴顶点光把 1024² 方位图洗成白片，bloom 再把白片摊满整屏（批 12 D）

门槛数字全绿（拾取、对位、进区、通路都对），截图里台面却是一整块发白的圆盘，区名与「45 本 / 265 章」读不出——塌的是画质不是逻辑。
三条叠乘：① 台面材质 `map` 与 `emissiveMap` 同一张图，`emissiveIntensity` 近台给到 1.25，图里最亮的字（`#f2e9d6`）直接顶到 1 以上；
② 一盏强度 32、`distance 10` 的点光悬在台面正上方 1.25 单位，`decay 2` 下中心辐照 ≈ I/d² = 32/1.56 ≈ 20，比台沿高一个数量级；
③ 全局 bloom `threshold 0.6 / strength 0.5 / radius 0.5` 把这些过采样点摊成白雾，半径 0.5 的雾正好盖住整张台面。

排查顺序：**先 `setBloom({threshold:0.999, strength:0})` 再截一张**——字立刻清楚就是 bloom 放大，不是贴图发白；
再用 `sampleLuminance(0.18,0.30,0.64,0.45)` 读台面区的 mean / p50 / `brightRatio` 定量。
本批落点：台面自发光 0.62/0.90、灯带 0.95/1.30、点光 14/18 并抬到 y 2.75（distance 10→12 把热点摊开），
展柜射灯 2.0/2.2；台面区 mean 0.511→**0.367**、p50 0.434→**0.235**、亮部占比 26.3%→**16.0%**，字口读得出。

教训：**发光体的可读性判「亮部占比」，不判「平均亮度」**——平均 0.5 也可以是整屏白。
抬灯比降灯更划算：降强度会连带把地面亮度拉下水（本批地面判据线 0.06），抬高 + 加大 `distance` 两头都保住。

### 83. 台面文字按「字头朝外」排，站在自己那一侧的台边读是倒字（批 12 A）

`indexDeskTexture` 里 `g.rotate(s.am + Math.PI/2)` 让字头指向台外，注释写的理由是「人在台边低头读，字头朝外最省力」——反了。
人站在台边看向台心时，屏幕上方对应的正是**台心方向**，所以字头必须朝台心（`s.am − Math.PI/2`）。
改完 `desk-sector.png` 里正对玩家的「数学 45 本 265 章」正立可读；隔着台面读对侧扇区仍是倒字，这是罗盘桌的固有性质，
走到那一侧就正了——不做双面绘制，同一区画两遍会让扇区账与 `triSector` 拾取账打架。

教训：**圆形台面上的文字朝向要用「读者站位」判，不能用「俯视图好不好看」判**；截图必须有一张站在读者位置的，
俯视特写会把倒字看成「角度问题」而放过去。

### 84. `Raycaster` 取的是 `camera.matrixWorld`：瞬移后不更新矩阵，准星算的是「转身之前」（批 12 D）

近台默认提示断言连续两轮读数不一致：一轮 HUD 是「六区索引 · 准星选扇区」，另一轮变成「数学 · 45 册 · 点击进入阅览室」，
而 `walk()` 报的 `yawDeg/pitchDeg` 两次都对。根因：`refreshAim → pickAt(ndc(0,0)) → Raycaster.setFromCamera`
是从 `camera.matrixWorld` 反推射线方向的，`camera.rotation` 改了但矩阵要等下一次 `render()` 才更新，
于是探针（以及任何瞬移：进出房间、退出漫游、`walkSnap`）拿到的命中属于**上一个朝向**。
修法一行：`refreshAim` 开头 `this.camera.updateMatrixWorld()`。

教训：**字段与矩阵是两套状态**，凡是「设完相机立刻取证」的接口都要自己把矩阵刷新；
读数随测试顺序漂时，先怀疑这类隐式时序，而不是先给断言加容差。

### 4. 超大仓库

`ACM-XCPC-Notes` 481MB、`kaoyan-math-66000` 38MB、`ai-enlighten` 17MB。

**「不要 clone」是有条件的，不是禁令。** 原句「不要 clone，只抓 `manifest.json` 与说明文件」保留为默认取向

- 50–100MB：`--filter=blob:none --sparse`，至少含根目录，按需再展开子目录
- \> 100MB，或只需要根目录的站：稀疏检出，只取 `*.md` 与 `*.json`

`ACM-XCPC-Notes` 481MB 走第三档；`kaoyan-math-66000` 虽只 38MB，但只用到根目录题库 JSON，同归第三档；
`ai-enlighten` 17MB 可浅克隆。硬约束：**稀疏规则不得排除正文所在子目录**——hello-ai 的正文在
`01-Hello-AI人工智能导论/` 下，被 `/*` 这类根目录规则挡掉就会把 `full` 站误判成 `stats-only`。

clone 失败或档位不明时退回 raw 逐文件（`schema.md` 第三节），别硬拉。

页面出问题时按此顺序查，别跳：

1. 控制台有无报错
2. 公式是 KaTeX 还是等宽字 → 查「反引号」
3. 图不出来 → 查 Mermaid 是否走了 CDN
4. 断网刷新白屏 → 查离线内联
5. 图片/字体 404 → 查 `\u002F` 或中文名编码

7. 3D 卡死 → 是否加载了分片外的数据
8. 正文里出现 HTML 标签字面 → `bodyType: "html"` 的站被当 Markdown 渲染了（见已验证 10）

    判据顺序是先位移后时长（`docs/design.md` 15.5）
45. 准星命中与 HUD 不符 → `walkAimSpine(i)` 会把人摆到脊前 1.9 单位再强制重读；手动摆位时也要走
    `walkSetLook(yaw, pitch)`，它内部调 `refreshAim(true)`，直接改 `camera.rotation` 不会刷新准星账
46. 漫游断言绿了但读数是 `{"x":0,"y":0,"w":0,"hidden":true}` → 判据在**元素还没出现的时刻**量盒，谓词退化成常量
    （见已验证 77）。凡按「指落点才生成」的浮层（摇杆底盘），几何判据必须挪到按下之后取实时盒
47. 漫游里「眼前一圈墙」→ 先读 `hallSightScan(25)` 的 `at` 与 `dirs[].wallDist/wallRole`，它量的是**站立点到最近内容的距离**，
    不是亮度；再用 `hallAudit()` 看内容件是不是都落在 `content` 组（角色名漂了会被算成墙，见已验证 81）
48. 展柜 / 装饰件「画上了但走不对」→ 网格实测与碰撞实测**两条断言都要有**（柜圈半径 vs `walkGapAt` 间隙），
    只断言一边会放过 Vec3 分量取错这一类（见已验证 79）
49. 门洞对位扫描读不到通孔（`holes: []`）→ 目标只留 `hallWall` 外壳：穿洞的射线会落到对面墙（>60），
    被堵的打在 ~44；把 `facades` 放进目标时门面就在洞口外一单位，六段通孔全被压成 45.8（见已验证 80）

50. 发光几何「数字全绿但截图糊成白片」→ 先 `setBloom({threshold:0.999, strength:0})` 复截一张分清「贴图发白」与「bloom 放大」，
    再 `sampleLuminance` 读该区间的 `brightRatio`（>0.75 占比）；判可读性用亮部占比，平均亮度会骗人。
51. 台面 / 圆盘上的文字读着别扭 → 先确认读者站位在**圆周外侧**：字头应朝圆心（`rotate(am − π/2)`），朝外就是倒字。
52. 探针读到「上一个位置 / 上一个朝向」的命中或 HUD → 查 `camera.matrixWorld` 是否在新朝向之后更新过
    （`refreshAim` 已补 `updateMatrixWorld()`）；字段值对而射线不对，是矩阵没跟上。
